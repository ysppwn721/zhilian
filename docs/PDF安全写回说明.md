# PDF 安全写回说明

## 产品口径

知链对 PDF 的默认输出是**勘误表**，原始 PDF 保持不变。PDF 是最终排版结果，文本以坐标指令保存，不具备 Word 的段落和 run 结构；直接改数字可能使数字签名失效、字体缺字、文字重叠，或让正文和表格出现不一致。因此，PDF 写回只定位为用户明确要求时使用的应急修复，正常路径仍是修改源 Word/Excel 后重新导出 PDF。

## 已落地的预检模块

`zhilian/pdf_writeback.py` 提供三个只读能力：

- `preflight_pdf_writeback(path, changes, ...)`：在任何写回动作前检查页数、文字层、签名、旧值出现位置、表格/图表信号和字体字形状态。
- `verify_pdf_writeback(original, modified, changes)`：对候选修改版做二次验证。
- `build_errata_markdown(preflight, changes)`：生成零修改的勘误表 Markdown，可作为后续 PDF 勘误表生成器的输入。

在需要运行 PDF 支线时安装可选依赖：`pip install -r requirements-pdf.txt`。桌面 Office 基础运行时不需要这些包。

写回项使用一页一项的结构：

```json
{
  "page": 12,
  "old": "6.04",
  "new": "5.80",
  "anchor": "营业收入",
  "source": "事实表 revenue_current",
  "source_value": 604539544.17,
  "source_unit": "元",
  "equivalent_values": ["604,539,544.17"]
}
```

`source_value` + `source_unit` 是推荐写法。预检会自动按元、万元、亿元生成常见小数位、四舍五入和截断形式，再检索全文；例如正文的“6.04 亿”和表格的“604,539,544.17”不共享同一字符串时，也可以被保守地识别为重复来源。`equivalent_values` 仍可用于补充行业自定义显示形式。没有可解析的来源事实值和单位时，预检会降级为勘误表，不把“未找到重复”当成“没有重复”。

也兼容现有变更报告使用的 `before` / `after` 或 `old_value` / `new_value` 字段。

## 决策规则

预检返回三种决策：

| 决策 | 含义 |
| --- | --- |
| `errata_only` | 只生成勘误表。默认结果；字体或签名状态未知、未获得用户确认、或调用方未显式打开写回开关时使用。 |
| `writeback_allowed` | 仅表示预检通过，未来写回器才可以继续；仍必须生成新文件，不能覆盖原 PDF。 |
| `reject` | 禁止修改版。存在签名、无文字层、旧值不存在或不唯一、目标页出现表格/图表候选、或字体明确缺少字形。 |

只有下面条件同时满足，才可能返回 `writeback_allowed`：

1. 没有数字签名；
2. 目标页和文档满足文字层覆盖要求；
3. 旧值在全文只有一个可定位的目标出现；
4. 目标页没有需要同步处理的表格或图表信号；
5. 新值的字形覆盖检查为 `safe`；
6. 用户明确确认，并且调用方显式传入 `allow_writeback=True`。

无法确认的状态不会被当作安全通过。当前运行环境没有 `fontTools` 时，字体状态为 `unknown`；这表示“没有证明字形安全”，不是“字形已校验通过”，因此默认只能输出勘误表。

## 为什么要拒绝“只改正文”

同一个指标经常同时出现在正文、表格和图表中。如果正文从 `6.04 亿` 改成 `5.80 亿`，而表格仍是 `604,539,544.17`，工具会制造新的文件内矛盾。预检会对旧值做全文检索；出现多个位置，或目标页呈现表格/图表信号时，直接拒绝正文单点写回。无法判断时也降级为勘误表。

## 修改版的四项验收

任何未来写回器都必须在重新打开修改版后通过：

1. 页数与原 PDF 相同；
2. 所有未修改页的文本 SHA-256 与原 PDF 完全相同；
3. 旧值在目标页减少/消失，新值可以被独立抽取；
4. 输出为新文件并带“事后修改/非原始文件”说明，不覆盖原文件。

`verify_pdf_writeback` 已实现上述机器可查的四项中的页数、未修改页哈希、旧值目标页消失和新值独立抽取检查。目前没有启用的生产写回器，因此二次验证逻辑只在合成夹具上验证过，不能表述为“真实修改版已经验证”。字体、签名和版式的视觉检查仍需在生成修改版后渲染页面并人工复核，不能只依赖文本抽取。

## 推荐工作流

```text
PDF → 文字/表格/图表识别
    → 论断与事实核验
    → preflight_pdf_writeback
        ├─ reject       → 只报告原因
        ├─ errata_only  → 生成勘误表，原 PDF 不动
        └─ writeback_allowed + 用户确认
             → 生成独立修改版
             → 重新抽取 + verify_pdf_writeback
             → 渲染检查后交付，并保留原 PDF
```

当前版本没有实现一个“强行改写任意 PDF”的写回器，这是有意的安全边界：在字体、签名、表格/图表同步和坐标版式均无法证明安全时，工具只报告，不伪造成功。

## 修订版 PDF 的安全替代路线

如果业务必须拿到一份 PDF 结果，使用确认后的 Word 重新导出独立文件，而不是覆盖原 PDF。`zhilian/pdf_revised_export.py` 提供 Word/LibreOffice 导出、SHA-256 清单和重新读取验证。它验证的是“新 PDF 可读且包含预期文字”，并额外报告页数是否变化；页数变化表示版式保真尚未证明，需要人工查看后再交付。现有 183 页年报实测中，当前正文重建 Word 导出为 268 页，说明这条路线可以生成可读修订版，但不能称为原版式复制。`pdf2docx` 在 20 页 born-digital 样本上约 6 秒、表格接近原稿，但必须在完整文档上重新验证。
