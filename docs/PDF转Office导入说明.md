# PDF 转 Office 导入说明

## 方案定位

知链不直接修改 PDF。PDF 进入项目时，先生成两份可维护的 Office 中间文件：

- `正文提取.docx`：保存文字层内容，按原始页码分节，用作论断来源；
- `事实表候选.xlsx`：保存通过表格结构解析和数值校验的候选事实，用作事实源候选；
- `转换清单.json`：保存原 PDF SHA-256、产物路径、页数、事实数、表格数和图表候选数。
- `文字锚点.json`：保存原 PDF 文字层的页码、坐标框、原文片段和锚点 ID；后续核验以它和原始 PDF 为准，不以重建后的 Word 作为唯一证据。
- `论断候选.jsonl`：按原始页码切分出的规则论断候选。它只用于智能体候选召回和人工确认，不直接写入事实或修复文件。

实现入口是 `zhilian.pdf_office_export.export_pdf_to_office`。原始 PDF 始终保持不变。

## 生成的 Excel

`事实候选` 工作表使用知链事实表的七个标准列：事实ID、主体、指标、期间、数值、单位、统计口径，并附加来源文件、来源页、表格编号、表格行、提取状态、独立交叉校验和校验状态。事实状态默认为“待确认”，不能把程序化抽取结果直接当作人工真值。`独立交叉校验=是` 只表示该表格行同时存在当前值、上期值和报告自带的变动字段，并且可进行结构计算；它不等于人工核验。

`表格校验` 保存变动比例的交叉计算结果，`表格原文` 保存逐单元格的原始表格内容，`转换摘要` 保存文件哈希和处理统计。

## 生成的 Word

Word 只承载 PDF 文字层，不把文字中的数字自动提升为事实。每一页以“第 N 页”为标题，保留原始页码对应关系；没有文字层的页面会明确标记为扫描页或纯图页。

## 后续维护

1. 用户先在 `事实表候选.xlsx` 中确认主体、指标、期间、单位和口径；
2. 将确认后的 Excel 与生成的 Word 一起加入知链项目；
3. Excel 发生变化时，沿用现有事实影响分析和 Office 修复链路；
4. Word 发生变化时，重新提取论断并重新关联事实；
5. PDF 图表不自动猜测数值，保留为图表候选和人工复核记录。
6. 用户确认修复后的 Word 后，可调用 `zhilian.pdf_revised_export.export_docx_to_pdf` 生成独立修订版 PDF；原 PDF 保持只读，并用 `verify_revised_pdf` 重新读取检查页数和文字层。

Word 普通正文不能直接作为事实源。只有具备完整事实表表头的 Word 表格，后续才考虑提供“候选事实导入”功能，并要求用户确认。

## 网页与后端入口

网页“导入文件，建立项目”窗口中的“从 PDF 导入并生成 Word / Excel”按钮调用
`POST /api/projects/from-pdf`。接口完成转换后自动创建项目，并在项目来源页显示原始 PDF 的只读下载入口。
原始 PDF 保存在项目版本目录的 `pdf_origins/` 下，归档 ZIP 也会保留它；任何转换或后续修复都不会覆盖原 PDF。
PDF 项目来源页还提供“生成修订版 PDF”按钮，对应 `POST /api/projects/{id}/pdf-revised`。它只读取当前 Word 版本，生成 `pdf_revisions/` 下的新文件，并提供独立下载和转换清单；页数变化会在页面上显示为“需视觉复核”。

服务器默认在可选依赖存在时选择 `pdf2docx`，缺少依赖时自动回退 `native`。也可以显式设置 `ZHILIAN_PDF_DOCX_BACKEND=native` 或 `ZHILIAN_PDF_DOCX_BACKEND=pdf2docx`。转换清单会记录实际后端，便于复现实验和审计。

## 当前边界

- 当前项目创建接口仍要求一份 `.xlsx` 事实源，Word 是论断/成果文件；
- PDF 转 Office 模块已经接入网页端的一键 PDF 项目创建入口；没有可用事实时接口会拒绝直接建立项目，并提示先整理候选 Excel；
- 扫描 PDF、复杂表格、图片图表和乱码文字层仍需人工复核；
- 原 PDF 不会被覆盖，也不会在转换时被修改。

## PDF 到 Word 的转换后端

默认的知链重建器保留页码、文字坐标和审计锚点，适合审计主链路。实验环境另外支持 `zhilian.pdf_revised_export.export_pdf_to_editable_docx`，内部使用 `pdf2docx`；它对普通 born-digital PDF 的表格和多栏排版更接近原稿，但仍可能改变分页、字体和复杂表格结构，因此只能在 `ZHILIAN_PDF_DOCX_BACKEND=pdf2docx` 或调用方显式选择时启用，不能宣称任意 PDF 原样复制。

知链与普通在线 PDF 转 DOC 服务的差异在于交付闭环：在线服务通常只返回一个 DOC/DOCX 文件；知链同时保留原 PDF 哈希和文字坐标，生成事实候选 Excel、论断候选、交叉校验记录和变更报告，并能把用户确认后的 Word 再导出为独立修订版 PDF。这样转换结果可以回到“哪一页、哪一行、哪条事实、谁确认、改了什么”的审计链，而不是一次性转换后无法追踪。公开年报对照实验中，`pdf2docx` 让 183 页样本的重导出页数从 native 的 268 页降到 184 页；最新同机证据包阶段为 74.525 秒，Word 导出为 5.102 秒。因此它是版式后端选择，不是把成熟转换器本身当作创新。

修订版 PDF 由确认后的 DOCX 重新导出：Windows 优先使用本机 Microsoft Word，Linux/macOS 使用 LibreOffice。导出结果必须经过重新读取和逐页视觉比对；页数变化、文字层差异、像素差异、字体替换或内容未找到时，状态为 `needs_visual_review`，向用户提供差异页和差异区域，下载接口返回 409 并阻止正式交付，只交付 Word/Excel 和变更报告，不把它标成“已还原 PDF”。只有在严格比对通过时，才允许显示“视觉一致性通过”。

当前采用的 `pdf2docx 0.5.13` 是 MIT 许可的可选后端，源码随 Python 环境安装在 `site-packages/pdf2docx`；它已停止由上游主动维护，因此项目只把它作为可替换转换器，不直接修改第三方包本体。
