# 打乱集结果与下一步计划（2026-10-05）

## 1. 当前结果如何解释

150 题人工 Gold 已完成候选顺序打乱，固定种子为 `20261004`，候选集合、标签和事实文本均保持不变。当前结果可以作为**位置伪影修复后的 v1 对照证据**。

| 策略 | 本期 Top-1 | 上期 Top-1 | 增长双来源精确匹配 |
|---|---:|---:|---:|
| 零信息基线（选末尾） | 8% | 15% | 0% |
| 纯规则（字段匹配） | 100% | 100% | 32% |
| BGE | 90% | 90% | 58% |
| BERT v1 | 96% | 8% | 6% |
| BERT v2 | 96% | 0% | 70% |
| 年报修正版 BERT | 68% | 98% | 100% |
| BGE + BERT 等权 RRF | 86% | 94% | 90% |
| 固定任务路由 | 90% | 90% | 100% |
| 纯 API（deepseek-flash） | 100% | 100% | 96% |

纯 API 结果为 150/150 题、60.1 秒、约 ¥0.1974、失败请求 0；完整记录见 `human_gold_eval_20261004/human_gold_pure_api_report.json`。

当前结果不能直接解释为“模型全面超过规则”。本期和上期单值题的题干已经明确给出指标、期间和口径，规则按字段匹配达到 100% 是设计预期。这一部分主要验证路由是否破坏确定性结果，不能单独证明语义能力。

数据口径更正：`annual_reports_weak_training_repaired_20261004` 的 train/dev/test 正例已经按本期与上期配平；此前提到的 `annual_reports_final` 中 1,029 条“总选本期+合并”属于另一份旧语料，不能用于解释修正版模型的训练分布。修正版模型在自带 test 与人工 Gold 上都呈现“本期低、上期高”，因此下一步要审计句式、数字位置和分数阈值，而不能再归因于期间硬编码。

真正有区分度的是增长双来源、同期间不同指标干扰、同义表达、期间隐含表达和需要拒答的题。当前 150 题中，增长题已经显示出专业化差异：年报修正版 BERT 和固定任务路由为 100%，纯 API 为 96%，说明路由和任务专门化比单纯增加模型数量更重要。

## 2. 下一阶段顺序

### P0：先落地确定性路由，再建立真实语义基准

当前最具性价比的候选路由是：

- 单值引用：先走纯规则；只有规则返回零候选或多候选时，才调用 BGE/本地 reranker；
- 增长率论断：优先使用年报修正版 BERT 召回本期、上期两个来源，再由规则校验增长方向、数值和期间；
- 任一路由低置信、口径不明或来源集合不完整：拒答并进入人工确认。

年报修正版 BERT 当前是约 409 MB 的 PyTorch 权重，现有线上 reranker 接口默认加载 BGE ONNX。因而“增长题使用年报修正版 BERT”先作为 CUDA 研究配置，不能直接写成已进入 Windows/macOS/Linux 安装包；要产品化还需完成 ONNX 导出、量化、CPU 延迟和内存验收。

在 v1 表格上，这个组合的离线结果可写成“单值规则 100% + 增长修正版 BERT 100%”，但这是**固定任务路由的研究上界**，因为评测脚本使用了已知 `task_type`。产品实现必须由规则解析和论断结构自动识别任务类型，不能读取 Gold 标签。自动任务识别的准确率、误路由率和拒答率要单独报告。

### P1：冻结 v1，建立真实语义 v3 基准

1. 保留当前 150 题及 SHA256，不再修改，作为“候选顺序修复”证据。
2. 不把当前 `annual_benchmark_repaired_20261004_v2` 的模板化 claim 当作语义泛化证据。它可以保留为弱标签工程诊断集，但不能替代人工 Gold。
3. 新建 240–360 题人工复核 v3，题目必须来自真实年报文字层，且 claim 中保留实际数值或真实自然表达。**单值题也必须包含真实数值**，例如“公司披露营业收入 12.5 亿元”，不能继续使用只明示指标和期间的模板。按以下任务分层：
   - 含真实数值的同义改写：营收 / 销售收入 / 营业总收入 / 销售金额等，约 25%；
   - 同期间、同主体、不同指标的真实干扰，约 25%；
   - 本期 / 上期 / 报告期等隐含期间表达，约 20%；
   - 增长率、百分点变化和双来源集合，约 20%；
   - 信息不足、口径冲突和应拒答样本，约 10%。
4. 每题至少包含同指标本期、上期事实，以及同期间不同指标、同指标不同口径或单位的真实干扰；增长题必须同时标注本期和上期来源。
5. 本期正确和上期正确配平；候选顺序用固定种子随机化；每题保留原始候选集合和打乱前后哈希。
6. v3 与训练公司、训练文档按公司隔离，人工 Gold 不进入训练集；先做 20 条逐条复核试运行，再批量构造。

另外增加一组不计入主分数的反事实检查：对同一事实对只交换“本期/上期”表达，或只交换本期与上期数值，验证模型是否随期间和数值同步改变选择。该检查要同时在人工 Gold v1/v3 和年报修正版模型自带的 `train/dev/test.jsonl` 上运行，用来区分句式、数值位置和评分阈值造成的偏差；不能把反事实样本当作新的独立年报样本。

v3 每条样本至少保存以下溯源字段：`source_file`、`source_page`、`source_bbox`、`source_sentence`、`claim_text`、`metric`、`value`、`unit`、`period`、`scope`、`gold_fact_ids`、`candidate_role`。`source_sentence` 必须能在 PDF/Word 文字层中原样定位；人工改写要同时保留原句和改写原因，不能只保留程序拼接模板。

### P2：统一重跑全部策略

在同一 v3 数据、同一候选集合、同一随机顺序上重跑：纯规则、BGE、BERT v1、BERT v2、年报修正版 BERT、RRF、固定路由和纯 API。每个策略保存版本、配置、耗时、失败请求、token 和费用。

指标统一为：

- 单值引用：Top-1、Top-2 召回、集合精确匹配；
- 增长论断：来源集合精确匹配、集合 Precision/Recall/F1；
- 拒答任务：覆盖率、拒答率、错误关联率、拒答准确率；
- 系统指标：P50/P95 延迟、API 调用次数、输入/输出 token、估算费用；
- 稳定性：候选顺序重排前后预测集合一致率。

### P3：先做路由校准，再决定是否继续训练

保留规则作为确定性入口：字段、期间、单位和数值关系明确时直接采用规则；零候选或多候选时调用本地模型；本地置信度不足才升级 API。对单值和增长任务分别校准阈值，避免 BERT v2 “偏本期”和年报修正版 BERT “偏上期”的偏差互相放大。

融合顺序采用“规则硬约束 + 本地评分 + API 兜底”，RRF 只作为研究对照。任何模型都不能直接改文件，输出必须经过来源存在性、期间、口径和数值规则校验。

只有在 v3 上同时满足以下条件才继续训练：

- 相对未微调基线在同义改写和同期间干扰任务上有稳定提升；
- 不再出现固定选择本期或固定选择候选位置即可达到高分；
- 增长双来源集合 F1 和拒答准确率没有下降；
- CPU 体积、延迟和内存满足离线候选模型要求。

否则保留 BGE 或现有年报修正版模型作为研究对照，不把训练结果接入默认生产链路。

## 3. 交付与 PPT 口径

可以使用的表述：

> 在消除候选位置伪影后的 150 题人工 Gold 集上，纯 API 集合精确匹配为 98.67%。固定任务路由在增长双来源任务上达到 100%，说明本地模型与规则分工可以在不依赖每题 API 的情况下取得相同或更高的专业任务表现。

> 单值题中，纯规则达到 100% 是因为题干明确给出了指标、期间和口径；模型的价值主要体现在同义表达、跨期间判断、增长双来源和拒答任务，而不是重复完成字段匹配。

> 当前结果证明的是一套可审计的分层方案：规则负责确定性约束，本地模型负责语义候选召回，API 负责低置信难例。它不宣称某一个模型在所有任务上全面领先。

## 4. 验收门槛

- v3 的零信息基线不得接近模型结果，且不能通过固定期间或固定位置获得异常高分；
- 所有策略在同一数据版本、同一候选顺序上运行；
- 自动任务识别不得读取 `task_type` 标签；标签只用于最终分层统计；
- 150 题 v1 的文件、哈希和旧结果保持不变；
- API Key 不进入代码、日志、PPT 或交付包；
- API 失败时记录失败类型、批次和耗时，不生成伪结果；
- 所有最终数字可由单条命令复现，并标明人工 Gold、程序化语义集和弱标签年报集的边界。

## 5. 当前决定

先采用“单值规则优先、增长修正版 BERT 候选、规则核验、低置信拒答”的候选路由，记录为研究配置，不立即宣称生产准确率 100%。当前 150 题 v1 与模板化的 `annual_benchmark_repaired_20261004_v2` 只保留为历史诊断证据，不再用于新模型结论。暂停继续训练，先完成 v3 真实数值基准和统一重跑。训练是否继续由 v3 的独立结果决定；在此之前，生产默认仍采用规则约束下的本地模型召回与 API 兜底路由。
