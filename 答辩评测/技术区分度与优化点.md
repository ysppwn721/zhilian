## 零、先修正三处会影响答辩的口径问题

### 1. 65.71% 不是引擎的准确率，是脚本的准确率

`真实评测集说明.md` 原先把 `run_rule_baseline.py` 的 65.71% 写成"确定性规则 Top-1=65.71%"。这是错的：

`run_rule_baseline.py` 为了对合成数据集做快速回归，用固定指标名复刻了一套启发式逻辑，其中把所有 `threshold` 论断都判成"支出 vs 预算"。但这批数据里一半阈值论断的真实来源是销售额，且顺序与标签相反，于是：

| 论断类型 | `run_rule_baseline.py` | 产品真实路径 |
| --- | ---: | ---: |
| growth | 48/48 | 48/48 |
| quote | 104/104 | 104/104 |
| ranking | 32/32 | 32/32 |
| threshold | **0/96** | **96/96** |
| 合计 | **184/280 = 65.71%** | **280/280 = 100.00%** |

缺口 96/280 = 34.29%，**正好等于整体错误率的全部**——那 34.29% 是脚本的 bug，不是产品的。

### 2. 已补齐产品真实路径基线

新增 `run_engine_baseline.py`，走产品实际调用链 `office.read_facts → office.read_document → engine.extract_claims`，未匹配条目单独计数、不静默计 0：

```
事实 6 条，提取论断 280 条
数据集 280 条：匹配 280，未匹配 0，Top-1 280（1.0000）
  growth 48/48 · quote 104/104 · ranking 32/32 · threshold 96/96
```

分流结果：dev 231/231，test 49/49，错误关联率 0，误拒率 0。产物 `predictions_human_engine.jsonl`、`human_engine_metrics.csv`。

**口径边界**：该夹具标签来自确定性引擎在环的本地长文夹具，280/280 衡量的是"实现与标签一致"，属于封闭夹具自洽性，**不是行业泛化**。外部泛化证据只引用 36 份公开年报程序化压力集。

### 3. PPT 提示词里的数字是错的（已修）

`PPT_中文reranker训练结果文案.md` 给 PPT 生成 Agent 的提示词原文写"BERT 41.15% 与 BGE 95.66%"，与同文件表格、图表 SVG、指标 JSON 的实测值 **41.32% / 96.18%** 不符。已改为实测值并加了"不得改动"的约束。
图与数已经一致，只有这处提示词是旧的；这类不一致一旦被评委发现，会连带质疑所有数字。

### 4. 需要你决策：`real_human_eval_dataset.jsonl` 的标签字段与官方口径冲突

`执行清单进度.md` 与 `真实评测集说明.md` 都写明：该批标签**只能称为"双智能体一致性检查"，答辩材料不得称为真人双标或人工真值**。

只要评委或 PPT 生成 Agent 打开这个 JSONL，看到的就是"两位独立人类标注员"。**这是当前交付物里风险最高的一处**。我按你与 GPT 的分工没有擅自改这个文件，请决定：

### 5. "歧义拒答率 100%" 的归属要说清（我上一版的判断已更正）

`06_校赛5分钟答辩文案.md` 的安全卡片写"歧义样本：本地模型拒答率 **100%**"。这个 100% 是**本地 reranker 单独**的指标，卡片上必须限定为"本地模型开启时"。

**更正我上一版的结论**：我此前依据 `model_routing_report.json` 的旧版本报告过"产品歧义拒答率 0、30 条歧义全被链接"。那是**旧评测脚本的打分口径问题**，不是产品缺陷——旧版本把"API 建议"直接记成 link，而产品里这两条路径都必然经过人工闸门。GPT 在 `5754d73` 中已把口径改为：多候选论断的 API 建议只作为**附加选项**，计为 abstain，不当作自动关联。

独立复核当前版本（我自己逐条算，不引用报告结论）：

```
predictions_routed.jsonl  180 条
  Top-1            150/150 = 1.0000
  错关联            0 条 = 0
  歧义拒答          30/30 = 1.0000
```

与 `model_routing_metrics.csv` 的 `routed-rule-local-api` 三行一致，**该表可信**。

但仍有一条必须在报告里写明的口径不对称（见 `模型路由优化报告.md`）：零候选样本被 API 链接时记为 link，多候选样本的 API 建议记为 abstain。本批夹具 `zero_api = 0`，对该表无影响；换数据集复算时必须重申。

**答辩归属建议**：分层路由的歧义拒答 100% 来自两条确定性规则——"复合论断不拆给模型"和"多候选必转人工"——**不是模型能力**；本地 reranker 单独的歧义拒答率也是 100%，但它在本批夹具里一次都没被调用（`multi_local = 0`）。真正的安全网始终是人工闸门。

## 一、工程成熟度类区分点（这些是"做没做过真项目"的分水岭）

### 1. 把失败写成可执行断言

`tests/test_real_phrasing.py` 里有 4 条**断言"识别不到"**的用例（真实年报的 4 类表达缺口）。补齐能力时测试会失败，强制同步更新文档与评测口径。

绝大多数参赛项目只展示成功案例。把已知失败固化成回归测试，是"知道自己在哪儿不行"的工程信号，且不需要额外成本。

### 2. 三种口径并存且互不混用

| 数据集 | 规模 | 标签来源 | 允许用来证明什么 |
| --- | --- | --- | --- |
| `eval_dataset.jsonl` | 180 条 / 30 组 | 程序构造（含歧义、对抗） | 安全性与提示注入 |
| `real_human_eval_dataset.jsonl` | 280 条 / 25 组 | 确定性引擎在环的夹具 + 双智能体交叉标注 | 实现一致性回归 |
| `external_programmatic_holdout_all.jsonl` | 576 条 / 36 组 | 公开年报 PDF + 程序化规则 | 真实语料压力验证 |

图表上直接标注"程序化标签，不是人工真值"。**主动声明自己的标签不是真值**，比宣称 100% 更能取信。

### 3. 规则唯一层不消耗模型调用（已加测试固定）

`test_rule_unique_claims_skip_model` 断言：演示样例 10 条论断全部规则唯一时，外部请求 **0 次**，轨迹出现 `model_skipped`。

这可以直接讲成一个数字：规则能定的，一次 API 都不发。

### 4. 模型边界是不变量，不是承诺

现有测试已经覆盖：模型提出的 `claim_id`/`refs` 必须在白名单内（越界即丢）、模型自由文本不得进入审计或决策提示、密钥不得落盘、模型与规则分歧时必须转人工选择且**不改变原关联**。

答辩可以这样讲："我们没有让模型计算任何数字、没有让模型裁决、也没有让模型写文件——这不靠约定，靠测试。"

### 5. 复合论断是"类型化规则"，不是字符串匹配

排名、增长率、预算对比各有专门的语义：

- 增长率必须同时锁定上期与本期，方向词含"增加/减少/上升"，且"减少"必须号负（这条曾一度会静默反号，已修并加测试）；
- 预算对比必须左右两侧各自解析出指标，且期间和指标都要显式出现，否则宁可留空也不猜；
- 排名需要**完整的同口径比较集合**，缺一个可比对象时状态是 `unverifiable / source_conflict`，理由写明"排名至少需要两个对象"，而不是拿最像的一条充当"最高"的依据。

本轮把"比较集合"抽成 `engine.ranking_cohort()`，抽取与人工候选共用一处逻辑。

## 二、优化点（按性价比排序，每条附实测证据）

### P0 真实年报识别率 0.5%，是当前最大缺口

同一份真实年报（169 页、第 10–45 页、40,008 字、580 个含数字句子）：

| | 改规则前 | 改规则后 |
| --- | ---: | ---: |
| 引擎识别出的论断句 | 0 | 3 |
| 识别率 | 0% | **0.5%** |

对照合成语料 100%，差约 200 倍。**必须继续如实汇报。**

但可行路径已经验证：`pdfplumber.extract_tables()` 对年报财务表返回结构规整的表，可直接映射为引擎事实表，且"变动比例（%）"列能**独立交叉校验**引擎算出的增长率。

建议做最小闭环：**PDF 财务表 → 事实表 → 引擎核验叙述文字**。这一步做成，外部压力集就从"只能评 reranker"升级成"能评整条链路"，PPT 上也就有了真实语料上的端到端数字，而不只是模型排序数字。

### P1 候选预算统计口径不准（实测数字，功能不受影响但数字会讲错）

候选预算脚本（`analyze_candidate_budget.py`）与 `agent._candidate_buckets` 都用 `engine.best_facts()` 数候选。但对排名论断，`best_facts` 只会返回 1 条（"A产品销量最高"的文本里没有 B 产品的字样）。

实测交叉表（280 条）：

| `best_facts` 口径 | 条数 | 其中标签只需 1 条事实 | 其中标签需要 ≥2 条事实 |
| --- | ---: | ---: | ---: |
| 单候选 | 184 | 152 | **32（全部是 ranking）** |
| 多候选 | 48 | 0 | 48 |
| 零候选 | 48 | 24 | 24 |

也就是说：32 条排名论断被记成了"单候选"，而按标签衡量需要 ≥2 条事实的论断共 104 条，现有"多候选 48 条"低估了 56 条。

**影响范围要说准**：`_candidate_buckets` 对排名论断走的是"规则候选非空 + 复合类型 → unique"分支，所以**功能上没有漏候选**（抽取路径已用 `ranking_cohort` 拿到完整集合）；错的是 `model_routing.multi_candidate_claims` 这类**对外展示的统计数字**。修法很小：复合类型（growth/ranking/threshold/chart）不按词法候选数分档。

### P2 外部模型调用次数已按批合并（GPT 已完成，本条保留为复核项）

我原先的实测结论是：纯 API 逐组 25 次 / 67.20 s（均 2688 ms，p95 3723 ms），现分级路由 21 次 / 62.15 s，只有 1.08×。根因是 48 条零候选散落在 21 个文档组，API 是"每组一次"，论断数降 83% 而调用次数只降 16%。

**`zhilian/agent.py` 现已改为按 40 条一批合并调用**（`for start in range(0, len(api_claims), 40)`），`model_routing_report.json` 在 seed 集上记录 `api_batches_at_40: 1`。因此上面的 12× 估算已成为实现，**无需再改**；需要在 280 条夹具上复测一次真实调用次数与端到端耗时，把"估算"换成"实测"。

### P3 成本要按 `usage` 真值，不要按估算

现有 -73.5% 的省钱比例是**按字符估算 token** 得出的（全量 25 次 19,724 in / 10,288 out；分级 21 次 9,810 in / 1,584 out；DeepSeek 官方价 1 元/M in、4 元/M out，0.0609 → 0.0161 元）。

问题有两个：一是 token 不是实测；二是绝对金额只有几分钱，讲"省 73.5%"容易被反问"总共省了多少"。建议改成 `usage` 实测，并把表述限定为"同一批论断的上游调用量下降"，不要延伸到与商业产品的价格对比（那需要同口径的单位价，目前没有）。

### P4 跨条目口径一致性审计（竞品不做的语义差）

当前每条论断独立核验。真实报告的典型错误是：同一份文档里，同一（主体, 指标, 期间）被解析出**不同的单位或口径**（含税/不含税、合并/母公司、万元/元），两条单独看都能通过，但在文档层面自相矛盾。

确定性实现很便宜：按 `(subject, metric, period)` 分组，组内 `unit`/`scope` 不一致即告警。这是"文档级核验"与"字段级核验"的真正语义差，也是能写进区分点的东西。

### P5 交付物卫生

- `答辩评测/public_reranker_pairs.jsonl` 有 **51.57 MB**，GitHub 已给过大文件警告；审计结论是不采用公开英文对作为主训练集，建议移出仓库或加 `.gitignore`。
- 站点仍缺 macOS 下载卡片（`site/index.html` 只有 Windows / Linux / 安卓 / 源码）。
- `执行清单进度.md` 的回归数已从 198 更新为 250（本轮修了 3 个分级路由后的用例并新增 1 个路由用例）。

## 三、答辩口径（建议原话）

**问"你们规则到底多准"**：
> 在 280 条双智能体一致性检查集上，产品真实路径 280/280 与标签一致，错误关联率 0。但这个数字衡量的是实现与标签一致性，属于封闭夹具自洽性，我们不把它说成行业泛化。真实泛化我们另有 36 份公开年报的程序化压力集，并且明确标注它不是人工真值。

**问"真实文档上到底行不行"**：
> 不行，这就是我们最大的短板，也是我们主动公开的：同一份 169 页真实年报里，含数字的句子有 580 句，我们的规则只识别出 3 句，0.5%。我们已经验证了可行的补齐路径——PDF 财务表可以直接结构化，并且表里的"变动比例"列可以独立校验我们算出来的增长率。

**问"和商业产品比便宜多少"**：
> 我们不比单价。区别在架构：他们每次核验都必须把内容送到云端模型，我们规则层不发任何请求。同一批论断的上游调用量，我们降了大约七成——但这是估算口径，绝对值只有几分钱，我们不把它包装成价格优势。
