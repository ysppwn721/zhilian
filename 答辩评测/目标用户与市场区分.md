## 一、竞品现状：数据一致性治理已有商业方案

报告数字与源数据不一致，不是没人做过。市面已有成熟产品，且都已用上 AI：

| 产品 | 定位 | 形态 | 用户 |
| --- | --- | --- | --- |
| **UpSlide** | 财务与报告团队的质量保证 | Microsoft Office 插件 | 企业金融/报告团队，按用户订阅 |
| **CCH Tagetik Intelligent Disclosure** | 企业披露管理 | 企业级平台 | 上市公司财务与合规部门 |
| **WPS 365** | 表格跨表联动 | 金山生态内公式联动 | 个人/企业，以**表格跨表联动和云协作为主** |

**它们的共同特征**：

- 都面向**企业**，需企业采购、IT 部署与运维
- 都**依赖 Microsoft Office 或自建生态**
- 一致性判定**依赖云端大模型**（单一路径，无本地判定能力）

> UpSlide 有 AI Consistency Check，CCH Tagetik 提供 AI 驱动的披露文档校验。
> 这说明：**"用 AI 检查报告数字"已不是空白，不能宣称首创。**

> **一处必须说准的事实**：UpSlide **文档留在本地，只有 prompt 出域**。
> 官方文档同时说明，MCP server 不直接访问用户文档，云端返回 OpenAI 模型响应。
> 因此准确的比较是“文档处理位置不同”：UpSlide 在本地处理文档，但模型判定依赖云端；本项目可由规则和本地模型完成大部分判定。

## 二、模型架构对比（本项目的架构区分点）

这一节是"多模型协同"与"单一云模型"的差异，全部有据可查。

### UpSlide 的模型架构（引自官方文档）

```
Word/Excel/PPT 插件  →  HTTPS(TLS 1.2)  →  企业专属 Azure AI Foundry  →  OpenAI 模型
      本地                                       云端                      云端
```

官方 AI 治理文档原文要点：

> **"Data sent: User Information, prompt. Data retrieved: OpenAI response."**
>
> 每个 AI 功能（AI Assistant、AI Glossary、AI Consistency 等）**各有独立基准，必须分别通过**；
> 一个模型可能对功能 A 有效、对功能 B 无效，则**只允许用于功能 A**；
> 每次发新版重跑测试，标准随技术进步提高，**旧模型会被淘汰**。

**结论：单一路径、单一模型族、全云端，无规则引擎兜底、无本地模型。**

> ⚖️ **公平说明**：UpSlide 的**模型治理纪律明显强于本项目**（逐功能独立基准 + 版本回归 + 主动淘汰）。
> 这一点应当学习，而不是拿来当差异。本项目已按其思路做**分层评测与归因**。

### 对比表

| 维度 | UpSlide | 表里如一 | 证据 |
| --- | --- | --- | --- |
| 模型调用时机 | **每次 AI 功能都调云端模型** | **规则先判，只有规则定不了的才交给模型** | 实测：280 条中规则唯一项 0 次调用 |
| 本地模型 | 无 | ONNX INT8 reranker（可离线，已上线公网演示） | `zhilian/reranker.py` |
| 分层路由 | 无 | 规则 → 本地 reranker → API 兜底 | `agent.py` 调用链 |
| 离线可用 | ❌ 判定必须联网 | ✅ 规则可覆盖的论断不需联网 | 架构可证 |
| API 请求数（同规模报告） | 280 次 / 280 条 | **按 40 条一批合并，困难论断约 2 批** | `api_batches` 字段 |
| 单日费用护栏 | 企业订阅 | **按访客 + 全局双闸门，超限自动降级规则模式** | `zhilian/quota.py` |
| 模型评测 | 逐功能独立基准（较成熟） | 分层归因评测 + 能力边界实测（进行中） | 需补齐 |

> 引入按批合并后，请求数取决于批次数（每批最多 40 条），在 280 条夹具上约 2 批。
> 说"调用条数 −83%"是准的，说"请求次数 −83%"不准。

## 三、成本与泛用性：限定到证据能支撑的范围

### ✅ 可以说：同一模型下的上游 token 用量

**度量口径**：单份含 280 条论断的报告（真实长文夹具），同一模型下的 token 用量。
**为什么不看价格、只看 token**：若两套方案用同一模型，**上游成本比 = token 量比**，
这与具体厂商定价无关，是更稳的论证。

| 模式 | 调用次数 | 输入 token | 输出 token |
| --- | --- | ---: | ---: |
| 全量 API | 25 | 19,724 | 10,288 |
| **分层（仅零候选升级）** | 21 | 9,810 | 1,584 |
| 变化 | −16% | **−50%** | **−85%** |

**深层原因**：分层把 83% 的论断挡在本地，**输出 token 降 85%**，而调用次数只降 16%。这里展示的是同一模型下的上游调用用量，不据此推出产品价格或商业收益。

> ⚠️ **必须同时说清的限定条件（否则会被追问）**：
>
> 1. **这是上游调用成本，不是产品售价**。本项目未发布定价、无订阅体系，
>    **不能声称"我们比 UpSlide 便宜 X%"**——那是终端价格，无从比较。
> 2. 单份 280 条论断报告的绝对金额只有几分钱，不能用百分比制造“低价优势”。答辩只展示输入 token 降 50%、输出 token 降 85%，并说明这是同一模型、同一批论断的上游用量对比。
> 3. 规模扩大时费用会随**进入 API 的论断数量和 token 数**近似线性增长；规则和本地模型处理的论断不产生 API token。产品没有发布售价，因此不做终端价格预测。

如果按同一报告规模估算，1,000 份报告约为单份用量的 1,000 倍，10,000 份约为 10,000 倍；实际金额取决于当时模型单价、缓存、输入长度和 API 兜底比例。大规模时最有效的控制手段是扩大规则/本地模型覆盖、按 40 条批量请求、设置访客与全局额度，而不是宣称产品更便宜。

### ✅ 真正值钱的不是省钱，是"不产生这笔钱"

上面的算法只对**零候选那 48 条**收费。而关键事实是：

**83% 的论断（232 / 280）根本不需要联网，判定在本机完成。**

| | 企业级产品 | 表里如一 |
| --- | --- | --- |
| 判定是否必须联网 | **是，判定走云端模型** | **否，83% 本地完成** |
| 数据出域 | prompt 与用户信息出域 | **83% 完全不出本机** |
| 离线场景 | 不可用 | **可用** |
| 前置条件 | 有 Office + 有网络 + 有采购 | **三者皆不需要** |

**这条对特定场景是"能不能用"的问题，不是"贵不贵"的问题**：

| 场景 | 云端方案 | 本方案 |
| --- | --- | --- |
| 党政机关内部报告 | 数据不能出域，**直接出局** | ✅ 可用 |
| 金融机构未公开数据 | 需专门审批与专属实例 | ✅ 可用 |
| 高校科研未发表数据 | 存在合规顾虑 | ✅ 可用 |
| 无网络环境（内网/现场） | **不可用** | ✅ 可用 |
| 规模极大（十万份级） | 成本与数据暴露面同步放大 | ✅ 大部分本地消化 |

> **答辩口径**：**不要说"我们更便宜"，要说"很多场景下我们不需要产生这笔 API 用量，
> 也不需要把数据送出去"**。前者是定价问题，后者是架构事实。

### ⚠️ 关于模型本身的价格：不构成本项目的差异

有两点必须澄清，否则会被认为在偷换概念：

1. **本项目改用国内模型（如 DeepSeek Flash）会显著更低**——
   但那是**模型选型差异**，不是"多模型架构带来的节省"。混在一起讲是错的。
2. **UpSlide 跑在企业专属 Azure AI Foundry 上**，其模型单价
   **未在公开定价页静态披露**（Azure 定价页由脚本动态渲染，未能取得可比数字）。
   因此**本项目不做跨厂商单价对比**，只做同模型下的 token 量对比。

**结论：成本优势的准确表述是"上游用量降 50%–85%、且 83% 不出本机"，
而不是"我们比竞品便宜多少"。**

### ✅ 可以说：泛用性（四条架构事实）

| 维度 | 企业级产品 | 表里如一 |
| --- | --- | --- |
| **Office 依赖** | 必须安装 Microsoft Office | **不需要，直接读写 OOXML** |
| **联网要求** | 判定必须联网 | **可离线** |
| **平台约束** | 绑定 Windows + Office 生态 | **Windows / Linux 均可，提供两种安装形态** |
| **程序化访问** | 以插件交互为主 | **MCP 只读工具接口**（7 个工具），可被外部 Agent 调用 |
| **取得成本** | 企业采购流程 | **下载即用** |
| **来源审计** | 闭源 | **完整源码可审 + 260 项自动化测试** |

**泛用性的准确表述**：不是"功能更多"，而是**"在更多环境下可用"**——
企业产品要求"有 Office + 有网络 + 有采购预算"三个前提；
本项目**三个前提都不需要**。

> 行业专用产品（披露管理）本身即面向企业合规流程，其"专用"是定位选择，不是缺陷。
> 因此**表述为"适用面不同"，而不是"我们比它们更好"**。

## 四、我们的区分：架构事实，不是定位口号

| 维度 | 企业级产品 | 表里如一 | 性质 |
| --- | --- | --- | --- |
| **运行依赖** | 必须安装 Microsoft Office | **直接读写 OOXML，不装 Office 也能运行** | ✅ 架构事实 |
| **判定位置** | **云端模型判定**（文档本地、prompt 上云） | **本地即可判定**（规则 + 本地模型覆盖 83%） | ✅ 架构事实 |
| **费用** | 企业订阅（按用户） | **无订阅体系**（本项目未定价） | ⚠️ 仅陈述事实 |
| **成本结构** | 需 IT 采购与运维 | **单机运行，无需 IT 资源** | ✅ 事实 |
| **判定方式** | AI 黑盒判定 | **确定性计算（Decimal + 单位/口径约束）** | ✅ 可复现 |
| **能力边界** | 指出"可能不一致" | **最小改动修复 + 重新读取文件复核** | ✅ 可验证 |

**关键差异是最后两行**：

- 企业产品的 AI 校验只能给出"这里可能不一致"；**审计场景需要的是可追溯的证据**，而不是模型判断
- 企业产品**发现问题即止**；表里如一会**按字符锚点做最小改动，并重新读取生成的文件独立复核**

## 五、目标用户：三段式

### 核心用户（主推）

**学生、科研人员、高校与科研团队**

**为什么最匹配**——他们天然产出**文档三件套**：

| 材料 | 作用 | 与本系统的关系 |
| --- | --- | --- |
| **Word 报告** | 实验报告、论文、结题报告、成果报告 | 正文含数值结论 → **被核验对象** |
| **Excel 数据表** | 原始数据、统计结果 | **事实来源** |
| **PPT** | 开题、中期、答辩、汇报 | 含结论与图表 → **被核验对象** |

**典型痛点**：

- 数据复核后，报告与幻灯片里的数字要**逐篇手动改**，容易漏
- 「本期销售额较上期增长 25%」这类结论，**数据一变就要重算**
- 答辩稿与论文数据**互相不一致**，自己看不出来

### 扩展用户

**中小企业中需要对外提交材料的人**

- 项目申报、政府汇报、投标文件、年度总结
- 特点：有 Word 报告 + Excel 数据，但没有企业 IT 资源，也不会为核对数字买企业级订阅

### 未来方向（需要新增能力，暂不计入现有范围）

**纯表格场景（如小微商户的进销存对账）**

- 需求真实存在：多张表之间核对、月度与总账比对
- **但形态不同**：这类场景是「表 vs 表」对账，**没有含数值结论的 Word 正文**
- 本系统的核心能力（从 Word/PPT 正文定位数值论断）在此场景**用不上**
- 若要覆盖，需新增「表格对账」入口——底层已有 `engine` 的确定性计算与 `graph` 的依赖图，但**尚无对应产品入口**

> **答辩建议**：把这一条放在"未来规划"，不要当成现有能力讲。
> 若被问"能否用于小卖店"，如实回答："需要新增表格对账入口，当前版本聚焦含叙述文字的文档。"

### 为什么核心用户是学生与科研人员，而不是企业

这不是"我们规模小所以先做小场景"，而是**能力匹配**：

| | 企业披露/财务团队 | 学生与科研人员 |
| --- | --- | --- |
| 材料构成 | 以平台化披露文档为主 | **Word 报告 + Excel 数据 + PPT 汇报，三件套** |
| 数据修改频率 | 有流程、有专人 | **反复改，且没人复核** |
| 现有工具 | 有采购预算，会买 UpSlide | **不会为核对数字买企业订阅** |
| 部署条件 | 有 IT 部门 | **装个程序都嫌麻烦** |
| 判定要求 | 需要审计留痕 | 需要**可复现、能自己看懂** |

**关键推论**：企业产品的三个前提（有 Office、有网络、有采购流程），学生与科研人员**一个都不满足**——
而这三个前提恰好都是我们不依赖的。

## 五之二、政府与事业单位：架构更匹配，但有一道我们还没跨过的门槛

这一节是 2026-09-26 新增。**必须如实区分"架构匹配"与"已验证支持"。**

### 为什么说架构上更匹配

| 他们的约束 | 云端 SaaS 方案 | 本方案 |
| --- | --- | --- |
| 内部数据不能出域 | **直接出局** | 规则 + 本地模型可离线判定，绝大部分不出本机 |
| 内网无外网 | **不可用** | 可离线运行 |
| 采购与运维成本 | 需 IT 采购与运维 | 单机/内网部署，可浏览器访问 |
| 要求可追溯 | 模型黑盒判定 | 确定性计算 + 完整审计与版本回滚 |

### 但必须说清的门槛：国产操作系统（信创）

政府与事业单位的电脑**大多不是 Windows**，而是：

| 系统 | 现状 | 我们的状态 |
| --- | --- | --- |
| 统信 UOS（x86_64） | 自带 Python 3.7，低于我们要求的 3.8 | ⚠️ 需 PyInstaller 自包含包，**尚未实机验收** |
| 银河麒麟桌面 V10 | 同上，另有 kysec 强制访问控制 | ⚠️ 同上 |
| 飞腾 / 鲲鹏（aarch64） | 架构非 x86 | ⚠️ 需另构建，规则模式依赖可从系统仓库取 |
| 龙芯 / 申威 | loongarch64 / sw64 无轮子 | ❌ **只能规则模式**，本地语义模型上不了 |
| 鸿蒙 PC | 已上线「融合开发引擎」可跑 Linux 环境 | 🔬 **待实机验证**，若成立可复用 Linux 版 |

**我们选的路径是"后端部署 + 浏览器访问"**，而不是逐个系统出安装包：

```
信创内网服务器（一份后端，x86_64 或 arm64）
        ↓
UOS / 麒麟 / 鸿蒙 · 用自带浏览器直接访问
```

一次性绕开架构适配、Python 版本、kysec 策略、应用商店签名与信创目录认证。
这也不是权宜之计——**本产品本来就是 B/S 架构**，公网演示 `https://demo.zhilian.space/`
就是同一个形态，已经实测可用。

> ⚠️ **答辩纪律**：可以说"架构上适配信创环境、提供浏览器访问路径"；
> **不要说"已支持统信/麒麟/鸿蒙"**——我们还没有在真机上验收过。
> 详见 `docs/信创适配说明.md` 与 `docs/鸿蒙PC与信创验证清单.md`。

## 六、可量化的优势（用现有实测数据）

> ⚠️ **做 PPT 前必读**：本节比例的分母有两个来源，引用时必须标注——
> **83%（150/180）来自 seed/sanity 集**；**83%（232/280）来自长文夹具**。
> 两者不可混用，也不能说成"行业泛化"。
>
> 另：本节的 280 条长文夹具目前**正被改动**（预算 100→200，报告正文同步），
> 但 `real_human_eval_dataset.jsonl` 的 24 条标注未同步，
> 导致引擎真实路径由 280/280 掉到 256/280。
> **在夹具与标签重新对齐之前，本节数字请勿写进终版 PPT。**

| 指标 | 直接调用 API | 分层协同（规则 + 本地模型 + API 兜底） |
| --- | --- | --- |
| 事实关联 Top-1 | 0.868 | **1.000** |
| 错误关联率 | 0.011 | **0.000** |
| API 调用量 | **280 条全部送模型** | **只有零候选的 48 条送模型（−83%）**，且按 40 条一批合并 |
| 离线可用 | ❌ 不可 | ✅ 大部分场景可 |
| 数据出域比例 | 100% | **17%** |

**这张表是本项目最硬的对比证据**：不是"我们更准"（规则本来就准），而是**在保持准确率的同时，把成本、依赖和数据暴露面都降下来了**。

对"数据不出本机"有要求的场景（党政、金融、科研未公开数据），**云端 SaaS 直接出局**，这是架构决定的结果。

## 七、答辩口径（建议原话）

> 报告数字的一致性治理已有商业方案，如 UpSlide、CCH Tagetik，但它们都面向企业，需要采购订阅、依赖 Microsoft Office。
>
> 表里如一走另一条路：**不装 Office 也能运行、无订阅、判定可在本地完成**，用确定性计算而非模型猜测给出判断，并且**不只指出问题，还做最小改动修复并重新读取文件复核**。
>
> 我们的用户是 **学生与科研人员**——他们天然同时维护 Word 报告、Excel 数据与 PPT 汇报，数据一变就要逐篇手动改，正是这套系统要解决的问题。

### 若被问到成本

> 我们不与竞品比价格（本项目没有订阅体系）。
> 可比的是**同一模型下的上游用量**：单份 280 条论断的报告，
> 全量调 API 需 19,724 输入 + 10,288 输出 token；
> 分层方案只需 9,810 + 1,584，**输入降 50%、输出降 85%**。
> 根本原因是**83% 的论断由本地规则与本地模型完成，根本不到 API**。
> 更好的说法不是"我们省钱"，而是**"很多场景下我们不需要产生这笔费用，也不需要把数据送出去"**。

### 若被问到模型架构

> 我们的模型层是**分层路由**而非单一路径：
> 规则先召回并收紧候选，多候选交本地 ONNX reranker 排序，只有零候选或低置信才升级到 API。
> 这套架构的价值已实测：**错误关联率 0，输出 token 降 85%**。
>
> 我们参考了 UpSlide 的模型治理思路——**每个 AI 功能独立基准、逐版本回归**——
> 并对本项目做了分层归因评测。这一纪律是从竞品身上学来的。

## 八、需要避免的说法

| 不要这样说 | 原因 |
| --- | --- |
| 「市面上没有同类产品」 | 会被 UpSlide / CCH Tagetik 直接推翻 |
| 「我们要做国民级的」 | 无法自证，且会被追问用户量与获客方式 |
| 「小卖店也在用」 | 该类场景缺 Word 正文，与现有能力不匹配 |
| 「我们比企业产品更准」 | 没有同口径对比数据，且企业产品未公开指标 |
| **「我们比 UpSlide 便宜 X%」** | 本项目无定价与订阅体系，终端价格无从比较；可比的是上游 token 用量 |
| **「它们把文档上传到云端」** | 应原样说：**UpSlide 文档留在本地，只有 prompt 出域**。说错会被反证 |
| **「我们数据不出本机（全量）」** | 仅规则可覆盖的部分不出域；零候选仍会送 API。必须说清比例 |
| **「我们做了模型治理，比它们强」** | UpSlide 的逐功能独立基准更成熟；应表述为"我们采用了同样的评测纪律" |
| **用小基数放大节省比例** | 单份报告的绝对金额只有几分钱，只展示输入 token 降 50%、输出 token 降 85%，并说明金额会随 API 论断数量近似线性增长 |
| **「已支持统信 / 麒麟 / 鸿蒙」** | 尚未在真机验收；只能说"架构上适配、提供浏览器访问路径" |
| **「我们的识别率很高」** | 真实年报实测只有 **0.5%（3/580）**；合成语料上的 100% 不能外推 |
| **「鸿蒙也可以出安装包」** | 鸿蒙 NEXT 不支持 APK 与 Linux 二进制，原生应用须用 ArkTS 重写 |
| **「模型比规则准」** | 在夹具上两者一致；正确表述是**分工**（规则管词面、模型管语义） |

**主动说出竞品，并讲清架构差异，比声称"没有竞品"更可信。**

## 九、规则能力边界：为什么这套系统必须有模型（实测）

这一段回答一个必然会被问到的问题：**"规则已经和多模型效果一样了，那模型到底干什么用？"**

方法：**同一份事实表、同一批语义，只改措辞**（脚本 `答辩评测/measure_rule_boundary.py`）。

| 系统 | 能认出候选（召回） | Top-1 正确 |
| --- | ---: | ---: |
| 纯规则 `engine.best_facts` | **38.89%** | **33.33%** |
| 本地语义模型 BGE | — | **94.44%**（Top-2 内 100%） |

在项目夹具上两者一致，是因为**那批文本就是用事实表的词写的**。换成人会写的说法就崩了：

| 改写 | 规则 | 语义模型 |
| --- | --- | --- |
| 本期销售额为125万元（原句） | ✅ | ✅ |
| 本期**销售收入**为125万元 | ❌ 0 候选 | ✅ |
| 公司本期实现**营收**125万元 | ❌ 0 候选 | ✅ |
| 本期**费用**为80万元 | ❌ 0 候选 | ✅ |

**销售额 / 销售收入 / 营收 / 营业总收入 / 销售金额**——人一眼知道是同一个东西，
规则**一条都认不出**。这就是模型的岗位：**规则做词面召回，模型做语义召回。**

独立第二套实验（`semantic_rewrite_eval_v2`，72 条改写、432 行）结论一致：
规则 **19.44%**、BGE ONNX **87.5%**、微调 BERT v2 **54.17%**。

> ⚠️ **必须同时说的短板**：把同样的规则放到**真实年报**上，
> 169 页、580 个含数字的句子，只认出 **3 句（0.5%）**。
> 所以正确表述是：
> **"规则在规范文本上可靠、在真实语料上召回很低；模型补的正是这一段。"**
