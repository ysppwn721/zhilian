### ✅ 评审 §12 的 mcp 版本冲突是**误报**（评审方自我更正）

评审称"`mcp==2.2.0` 与 `mcp>=1.30,<3` 冲突，因为 2.2.0 < 1.30"。
这是把 `1.30` 误读成 `1.3.0`。实测（`packaging.specifiers`）：

```
mcp 1.30  in >=1.30,<3 -> True
mcp 2.2.0 in >=1.30,<3 -> True
mcp 1.29  in >=1.30,<3 -> False
```

**不冲突。** `requirements.txt` 已补注释说明这一点，避免后人重复踩。
（`requirements-dev.txt` 与 lock 的差异仍在，但不属"装不上"级问题。）

### ✅ P1 摘要缓存：只读请求不再全量重算 SHA256（评审 §6）

- 问题：`store.verify()` 在**每个读取类请求**上对全部文档重算 SHA256
  （`digest()` = `read_bytes()` 全量读），文档上限 500 份 ⇒ 开销与项目体积成正比。
- 处理：`office.digest()` 加 `(路径, 大小, mtime_ns)` 键的缓存。
  摘要只由内容决定，任何写入都会改 mtime/大小，不存在读到陈旧摘要的风险。
- 实测：8MB 文件重复取摘要 **22× 提速**；改动内容后正确失效；仅 touch 不改内容时摘要不变。

### ✅ P1 `_INDEX_CACHE` 判等逻辑修复（评审 §8）

- 原实现按键 `fingerprint` 取值，却拿 `entry['size']` 与 `len(facts)` 比较——
  同键必然同条数，该判断**恒假**，真正的失效场景（同条数不同描述符）反而漏网；
  且 `> 8` 条即整表清空，连续处理 9 张不同事实表后缓存归零。
- 实测修复前：30 张互不相同的表（指纹零碰撞）跑完缓存**只剩 3 条**；修复后正常驻留。

### ✅ P1 `extract_claims` 的记忆化（评审 §7）

- 同一段文本在一次抽取里会被重复求解：算 `source_text` 一次、按期间各一次、
  每个论断分支一次、循环末尾又一次。
- 处理：按 `(文本, 期间)` 记忆本轮结果。事实与索引在函数内是常量，记忆化不改语义。
- 实测：300 条事实的长文本块 **0.222s → 0.032s（6.9×）**，论断 ID 确定性不变。

## 三、两处根因判断（已处理）

**根因一：`华北五省设计/华北五省设计/` 快照目录** 同时制造了"源码双源漂移"和

**根因二：`site/static/` 与 `web/` 之间没有构建同步步骤**，靠手工复制，必然漂移。
已补 `sync_web_to_site.sh` 并由 CI 门控。同类问题还有版本号六处手工同步，
也已由 `sync_version.py` 收口。

**保留意见**：`site/downloads/` 与后端 `/downloads` 路由的职责仍未对齐——
后端 `PUBLIC_DOWNLOADS` 是精确匹配白名单，而站点走 Worker 静态资源，
两套机制各自维护文件名。版本号已收口，但"哪些文件该放哪一侧"仍靠人记。
