# Office 主线下一步优化计划

PDF 识别和写回支线暂时冻结，后续资源集中到 Word、Excel、PPT 的真实工作流。原因是单位和企业财务人员通常拥有 Word 源文件，直接在源文件上修复比 PDF 重建更可靠，也更符合项目定位。

## 优先级排序

### P0 多文档和大批量稳定性

目标是“一份 Excel 对应几十到上百份 Word/PPT”时仍然可用：

- 追加文档按批次处理，失败批次不影响已有版本；
- 增加文档级进度、失败原因和重试入口；
- 对相同文件哈希跳过重复解析；
- 事实表只解析一次，文档解析结果按文件缓存；
- 最终报告按文件、论断类型和状态汇总；
- 压测 10、50、100 份文档，记录耗时、内存和失败率。

当前基线已经完成 1 份 Excel + 100 份 Word + 24 页 PPT 的真实 HTTP 批量压力测试：103 个文件、3 个批次，最新同机复跑总耗时 8.41 秒（此前基线 8.31 秒），状态通过；10 / 50 / 100 份 Word 的独立规模实测分别为 0.75 / 3.30 / 8.41 秒。下一步不是重复证明“能导入”，而是补坏文件、重复文件、超限文件和中途失败后的恢复测试。

验收标准：单个坏文件不能导致整批回滚；每个输出文件都能追溯到输入文件、版本和事实来源。该验收已由容错追加接口和三组 API 回归测试覆盖：部分成功、重复文件隔离、全失败不改版本。

### P0 Excel 事实源质量

- 检查重复事实 ID、缺失单位、期间冲突和主体冲突；
- 支持公式结果读取与公式未计算提示；
- 对隐藏工作表、合并表头和空值做明确提示；
- 数值、单位、期间不完整时禁止进入自动修复；
- 在网页中显示“已交叉校验”和“仅结构候选”的区别。

已完成第一版质量门禁：导入时生成 `fact_quality` 报告，区分 `pass`、`review`、`blocked` 三档。重复 ID、缺失数值/单位/期间、公式、无法解析的数值和同一主体/指标/期间/单位/口径对应多个不同数值会进入 `blocked`，自动修复被拒绝；隐藏工作表和合并区域进入 `review`，允许继续导入但要求人工确认。网页“来源与文件”页显示扫描数量、问题代码和自动修复是否允许。新增 5 个回归测试覆盖清洁表、隐藏/合并、空值、冲突定义和修复门禁。

### P0 原生图表覆盖

当前图表只对受支持的原生单系列对象自动处理。已完成第一轮按风险分层：

1. 原生柱状图、条形图、折线图、饼图和圆环图的单系列对象继续支持；
2. 多系列且单绘图区的图表按系列拆成多个候选，每个系列独立显示、独立确认；只批准一个系列时，未批准系列会在重建时保留；
3. 图片图表、组合图、多绘图区图表和外部工作簿链接只输出复核提示，不自动猜测；
4. 修复后重新扫描生成的 PPTX，通过 python-pptx 重新读取图表缓存并以确定性核验确认新值。当前 Windows 环境已发现 Microsoft PowerPoint Office16，并用 `答辩评测/render_ppt_with_powerpoint.py` 实际导出 PNG 与 PDF；服务端修复流程仍不自动启动 Office，只把视觉渲染作为独立验收步骤。

新增回归覆盖：多系列识别、系列级候选、只修改一个系列时保留其他系列、缺失嵌入工作簿的重建、饼图/条形图/折线图读取。

### P1 语义模型和智能体路由

- 保留规则作为确定性基线；
- 本地 BGE 处理规则零候选和多候选语义召回；
- 低置信结果转人工，不自动升级为错误关联；
- API 只处理本地模型弃答或未覆盖的困难样本；
- 在冻结 dev/test 集上重新校准阈值，记录 Top-1、错误关联率、歧义拒答率、调用量和延迟；
- 不把合成数据上的结果表述为真实行业泛化能力。

### P1 用户流程和可解释性

- 核验页默认突出“已失效”和“待确认”，把仍成立的条目收进折叠区；
- 每条候选显示主体、指标、期间、单位、口径、来源文件和单元格；
- 人工确认前显示预期影响文件和字符区间；
- 修复后提供“变更前—变更后—重新验证结果”三列报告；
- 对未识别文本明确写“未覆盖”，不显示为通过。

### P1 工程交付和安全

- Windows、Linux、macOS 安装包做同一套冒烟测试；
- API Key 只从环境变量读取，日志和响应脱敏；
- 访客额度和全局额度双闸门继续保留；
- 记录模型模式、调用次数、耗时和降级原因；
- 源码、模型包、安装包和第三方许可证分开归档。

## 推荐的下一轮实施顺序

1. 先做 10/50/100 份 Word/PPT 批量压力测试和失败重试；
2. 同步补 Excel 事实源质量校验；
3. 再扩展多系列原生图表；
4. 最后根据新的困难样本重新校准本地模型和 API 路由。

这条顺序优先解决真实用户最容易遇到的规模和数据质量问题，再增加模型覆盖面，避免在输入质量不稳定时继续训练模型。
